# QA Automation Assessment — Testing Strategy

## 1. Testing Strategy

I focused the testing effort on areas with the highest potential business and security impact rather than attempting to achieve broad test coverage across every function.

The testing approach consisted of:

* Unit/business-logic tests using Vitest.
* Integration-style tests around validation and access-control server actions.
* API authorization and object-level authorization tests.
* One end-to-end buyer-to-admin journey using Playwright.
* Intentional expected failures for defects discovered in the existing implementation.

The main areas prioritized were:

1. Catalogue lifecycle and publishing.
2. Pricing and discount calculations.
3. Product import mapping and validation.
4. Authentication and authorization.
5. Catalogue/listing object-level access control.
6. Buyer enquiry submission and admin lead visibility.

---

## 2. Highest-Risk Area

The highest-risk area I identified was **catalogue publishing and access control**.

A catalogue is directly connected to what buyers can see, including product availability and pricing. The application also distinguishes between Staff and Admin permissions, with publishing and deletion intended to be restricted to Admin users.

Because of this, I prioritized:

* Draft vs Published behaviour.
* Published vs Expired behaviour.
* Staff vs Admin authorization.
* Unauthenticated access to protected functionality.
* Object ID tampering.
* Cross-catalogue listing modification/deletion.

The defects identified in these areas are documented in `FINDINGS.md`.

---

## 3. Unit and Business Logic Testing

I added focused tests for business logic rather than testing every implementation detail.

### Pricing

Tests cover:

* Discount percentage calculation.
* Price-on-request behaviour.
* Price labels.
* Required pricing before sale.

These areas were prioritized because incorrect pricing can directly affect commercial transactions.

### Catalogue lifecycle

Tests cover:

* Active published catalogues.
* Expired catalogues.
* Legacy inactive/expired status handling.

The lifecycle tests identified defects where future and past validity dates are interpreted incorrectly.

### Spreadsheet import

Tests cover:

* Automatic column mapping.
* Currency/number parsing.
* Duplicate SKU detection.
* Invalid quantity validation.
* Invalid image URL handling.

Import validation was prioritized because seller data can be inconsistent and incorrect imports can introduce bad product information into the catalogue.

### Input validation

Tests cover:

* Product name validation.
* Negative price rejection.
* Catalogue edit payload validation.

---

## 4. API and Access-Control Testing

The security testing focused on the difference between authentication and authorization.

The following scenarios were considered:

* Unauthenticated access to protected admin functionality.
* Staff attempting Admin-only operations.
* Admin performing permitted operations.
* Server-side permission enforcement.
* Catalogue ID tampering.
* Listing ID tampering.
* Cross-catalogue object access.
* Valid IDs combined with unauthorized/tampered data.

The important finding from this testing is that checking whether a user is signed in is not sufficient. The server-side operation must also verify that the authenticated user has the required role and that referenced objects belong to the intended parent resource.

The identified authorization defects are documented in `FINDINGS.md`.

## 5. End-to-End Testing

I implemented one end-to-end Playwright journey covering the primary buyer workflow:

```text
Published Catalogue
        ↓
Browse Product
        ↓
Open Product
        ↓
Contact Supplier
        ↓
Submit Enquiry
        ↓
Receive Enquiry Reference
        ↓
Open Admin Leads
        ↓
Search for Enquiry
        ↓
Verify Buyer
```

The test verifies both sides of the workflow: the buyer-facing submission and the resulting Admin Leads Inbox record.

I deliberately kept this to one end-to-end journey instead of creating multiple UI tests because the assessment asks for one reliable and readable journey.

The test currently passes:

```text
1 passed
```

### Waits and State

The test primarily uses Playwright's built-in locator waiting and assertions instead of arbitrary fixed delays.

For example, the test waits for:

* Product heading visibility.
* The enquiry dialog.
* The dialog title.
* The enquiry confirmation.
* The generated enquiry reference.
* The corresponding record in the Admin Leads Inbox.

### Test Data

The test uses the seeded catalogue and a unique buyer name/reference generated by the application during submission.

The Admin login uses the seeded assessment account when the application redirects the test to the login page.

### Selectors

I used semantic selectors such as:

* `getByRole`
* `getByText`
* `getByPlaceholder`

and specific IDs where they were appropriate for form fields.

This keeps the test relatively readable while avoiding unnecessary dependence on CSS implementation details.

### CI / PR Execution

For a production PR pipeline, I would isolate test data or reset the database before the E2E test so that repeated runs do not depend on state created by previous runs.

I would also run the E2E suite against a dedicated test database and use deterministic test accounts/data.

## 6. What I Deliberately Did Not Test

I deliberately did not attempt exhaustive coverage of every page, component, CRUD operation, or UI state.

Examples of areas not comprehensively covered include:

* Every individual admin UI interaction.
* Every product-management action.
* Every possible spreadsheet format.
* Every validation permutation.
* Visual/layout testing.
* Browser compatibility across multiple browser engines.
* Performance/load testing as part of the core assessment.
* Exhaustive API response-schema testing for every endpoint.

The reason was to prioritize defects that could have a direct impact on:

* Pricing.
* Catalogue availability.
* Publishing.
* Authorization.
* Data integrity.
* Buyer enquiries.

This provides higher-value coverage within the assessment time rather than maximizing the number of tests.

## 8. Codebase Quality Observation

One code-quality issue I identified is that authorization logic is not consistently centralized across all server-side entry points.

Some operations correctly use role-aware authorization such as `isAdmin`, while other server/API paths rely primarily on authentication.

This creates a risk where a new endpoint or server action can accidentally implement:

```text
authenticated user = authorized user
```

instead of:

```text
authenticated user + required role + resource ownership = authorized operation
```

### Proposed Improvement

I would introduce reusable authorization helpers for server-side operations, for example:

```text
requireAuthenticatedUser()
requireAdmin()
requireCatalogueAccess(catalogueId)
requireCatalogueListingAccess(catalogueId, listingId)
```

These helpers could consistently perform authentication, role validation, and resource ownership checks.

This would reduce duplicated authorization logic and make security requirements more explicit at each server-side entry point.

## 9. AI Usage

AI tools were used as a development aid during the assessment.

Specifically, AI was used to:

* Help understand the existing project structure.
* Suggest test scenarios based on the assessment requirements.
* Help draft initial Vitest and Playwright test structures.
* Help troubleshoot TypeScript/import/test execution issues.
* Review test failures and suggest corrections.
* Help organize the findings and testing strategy documentation.

The final tests were run against the provided application, and the test assertions were checked against the actual source code and observed application behaviour.

I reviewed and adjusted the generated code rather than treating AI-generated output as automatically correct.

---

## 10. Overall Approach

The overall strategy was risk-based rather than coverage-driven.

The main objective was to demonstrate that the automation suite can:

1. Detect existing defects.
2. Protect critical business calculations.
3. Validate potentially messy imported data.
4. Verify server-side authorization.
5. Detect object-level access-control issues.
6. Validate the primary buyer-to-admin business journey.

The automated tests and documented findings are intended to provide both executable evidence and a clear explanation of the observed defects.
